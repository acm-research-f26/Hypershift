# Prepared donor-window timing guard

Research_Plan §8.1 proposes earlier same-security feature-window donors. `research/analysis/rishi_donor_timing.py` provides a conservative, synthetic-tested chronology guard; it does not perform or authorize that intervention. A donor is accepted only if IDs match, its input window ends strictly before the recipient input window, and its label ends no later than the recipient decision and strictly before the recipient label starts. Both window/label intervals must have valid chronology and timezone-aware timestamps; the recipient decision must follow its window and precede its label. Timestamps are compared in UTC, so equivalent time zones compare consistently. Requiring the donor label to have finished before decision is deliberately stricter than nonoverlap alone.

Two focused tests exercise an admissible pair, wrong ID, equal window ends, label timing violations, malformed chronology, empty IDs, naive timestamps, equality at the decision cutoff, and conversion from New York time. The initial missing-module red test failed as expected; after implementation, an invalid test fixture initially raised the intended malformed-chronology exception and was corrected before green. All examples are synthetic. This checks represented timestamps only; it cannot verify when the vendor first published or revised data, identity continuity, exchange calendars or real donor support.

No choice of matching variables, scaling, tie-breaking, fallback, distribution-shift threshold, financial data, donor sample, trained checkpoint or outcome has been frozen here. Those remain part of a future before-outcome perturbation protocol after the strict checkpoint gate and any required data provenance are satisfied. No financial training, scoring or checkpoint tolerance change occurred. Implementation and tests are commit 2b78b85.
